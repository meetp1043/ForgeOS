# Architectural Principles

The development of ForgeOS is guided by these core principles.

### 1. Start with a Modular Monolith
**Principle**: ForgeOS will be built as a Modular Monolith using Spring Modulith, not as dozens of microservices from day one.
**Reasoning**: Microservices introduce extreme operational complexity (distributed tracing, network latency, distributed transactions, complex deployments). A modular monolith provides the internal code separation (cohesion and low coupling) of microservices without the operational tax. 
**Extraction Strategy**: If a specific module (e.g., the Execution Sandbox or Model Gateway) experiences unique scaling or security requirements, its strict internal boundaries will allow us to extract it into a standalone service later.

### 2. Technology-Specific Core, Technology-Agnostic Output
**Principle**: ForgeOS itself is unapologetically a Java/Spring Boot/React application. However, the *applications generated by ForgeOS agents* must remain technology-agnostic. 
**Reasoning**: We must not tightly couple our internal orchestration logic to the output capabilities of the agents. ForgeOS must be able to generate Python, Go, or Rust applications just as easily as Java applications.

### 3. Provider Independence (The Model Router)
**Principle**: The core system must never hard-code dependencies on a specific AI provider's SDK (e.g., direct OpenAI API calls).
**Reasoning**: AI models evolve rapidly. Costs, privacy concerns, and local hardware capabilities fluctuate. We abstract all model interactions behind a generic Model Router via Spring AI to ensure BYOK, Local AI (Ollama), and cloud provider fallback are first-class citizens.

### 4. Least Privilege and Secure Execution
**Principle**: AI agents are fundamentally untrusted entities when executing code or tools.
**Reasoning**: Agents can hallucinate or be victims of prompt injection. All tool executions (shell commands, file modifications) must occur within an isolated Execution Sandbox. Agents only receive the specific tool capabilities they require for a task.

### 5. Event-Driven Internal Decoupling
**Principle**: Cross-module communication should favor domain events over synchronous method calls where consistency allows.
**Reasoning**: This prevents tight coupling (e.g., the `Agent` module shouldn't need to know the internal API of the `Notification` module).
